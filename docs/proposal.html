01 Summary

The challenge has two halves, and the main design choice was to keep them strictly apart.

  • Transfer reliability. A chunked, resumable, hash-verified upload protocol survives bandwidth swings, latency, resets, stalls, blackouts, timeouts, path switches and corruption in transit. A file is accepted (COMPLETE) only when every chunk and the whole file match the SHA-256 values the client declared up front.
  • Frame integrity. A verified file is validated with ffprobe, fully decoded and checked for missing, duplicated and abnormal frames on a 30 FPS slot map. Every finding states its evidence, a confidence and a cause: transfer, capture/encoding, or bitstream damage.
The judges' key distinction is built into the design. A byte-perfect transfer proves only that the server's file equals the client's file. It cannot prove the recording had no dropped frames. Each report therefore gives the transfer verdict and the frame verdict separately, and treats repeats or omissions that come only from 30 FPS conversion as warnings, never as anomalies.

03 Approach: reliable transfer

The protocol assumes the network will fail mid-transfer and makes every step safe to repeat.

  1. Manifest first. The client sends the file size, the whole-file SHA-256 and a SHA-256 for every 256 KB chunk. The upload ID is derived from the file hash, so any later process can find the same session.
  2. Independent chunks. Each chunk is a separate PUT with a 4 s timeout. The server hashes the chunk before writing it (temp file, fsync, rename) and refuses it with HTTP 422 on mismatch.
  3. Retry with backoff. Failures are retried after uniform(0, min(3 s, 0.2 s·2ⁿ)). Full jitter keeps retries from synchronising on a weak link.
  4. Resume from the server. After any failure the client asks the server which chunks it holds and sends only the rest. The server is the source of truth, so a crashed client loses nothing.
  5. Failover. After 3 consecutive failures the client switches to the next endpoint (Wi-Fi → cellular style).
  6. Verification gate. Finalize is refused (409) while chunks are missing. The assembled file must match the declared SHA-256, or the upload is REJECTED. With no progress for 10 s the session becomes STALLED; after 600 s it is EXPIRED and its partial data is discarded.

04 Approach: frame integrity analysis

Analysis runs only on COMPLETE files. Each detector reads a different source of evidence, and the evidence sets the confidence. A finding is never stronger than the evidence behind it.

Evidence sourceDetectsConfidence
Container timestamps (PTS gap > 1.5× nominal interval)Missing / skipped frames, with time range and frame countHigh
Container metadata vs decoded frame countTruncated stream, undecodable framesHigh
Decoder error logBitstream damage, invalid containerHigh
Frame content: 32×18 gray thumbnails, mean abs diff < 0.05Duplicated / frozen framesMedium (low if scene is static)
Isolated motion jump with no timestamp gapPossible drop hidden by a re-encodeLow (hint only)
Client's pre-upload ffprobeShows that an anomaly existed before the transferReference

30 FPS slot map. Source timestamps are mapped onto a 30 FPS grid. Each slot records its index, time and source frame, and gets one of three labels: unique, gap_fill (no source frame exists, so the gap is real) or conversion_duplicate (the source simply runs at a different rate). This keeps conversion artefacts out of the anomaly count, which the brief explicitly warns about.

Cause attribution. If the transfer is hash-verified and the pre-upload probe already shows the gap, the anomaly is attributed to capture/encoding. Decoder errors are attributed to bitstream damage. A transfer fault cannot reach analysis at all, because such a file never becomes COMPLETE.

05 Major architecture decisions

AD-1Hash-gated state machine; analysis only from COMPLETE
Why"Upload finished" is not proof. Per-chunk plus whole-file SHA-256 means an accepted file is provably identical to what the client declared.
Trade-offThe client hashes the whole file before sending, which is a small one-off cost for a 30 s clip.
AD-2Server is the source of truth for resume
WhyThe upload ID is derived from the file hash and the server reports which chunks it holds. A fresh client process (after a crash or reboot) resumes with no local state. In T10 it sent only 1225 of 1737 KB.
Trade-offUploading the same file twice maps to the same session. That is intended deduplication.
AD-3Fixed 256 KB chunks with timeout, full-jitter backoff and failover
WhySmall chunks bound the work lost to any single failure at 20% signal. Full jitter avoids retry storms, and failover covers path changes.
Trade-offPer-request overhead on a good link. Adaptive chunk sizing is listed as future work.
AD-4Atomic, crash-safe writes
WhyEvery chunk and metadata write goes through temp file, fsync and rename, so a half-written chunk is never visible and a server crash cannot corrupt accepted data.
Trade-offOne extra fsync per chunk.
AD-5Seeded, in-process chaos proxy instead of manual Wi-Fi toggling
WhyEvery network scenario is reproducible (seed 2026) and runs in CI-like conditions with no root access. The fault clock starts at the first client connection, so results do not depend on machine speed.
Trade-offLoss is emulated at the TCP level (stalls, resets, slowdowns), not as dropped IP packets. tc netem would add that.
AD-6Evidence-tiered findings with explicit cause
WhyThis answers the brief's technical distinction directly. Every anomaly says what proves it (timestamps, metadata, decoder, content), how sure we are, and whose fault it is.
Trade-offReports are more verbose than a single verdict. The HTML timeline keeps them readable.
AD-7Zero dependencies: Python standard library + ffmpeg
WhyThe project runs anywhere ffmpeg runs, with no pip or Docker, and is easy to audit at ~1,900 lines.
Trade-offThumbnail diffs are computed in pure Python on 32×18 frames. This is fast enough for 30 s clips.
AD-8Ground-truth test videos and real-footage tuning
WhyDetection accuracy is measured on generated videos with known injected drops and freezes. Thresholds were then tuned on 7 real clips, which exposed flaws the synthetic videos could not show (see §07).
Trade-offReal clips have no ground truth, so their tests check that the pipeline is sound, not that the recording is clean.

07 Tuned on reality

Synthetic videos passed from the start. Real footage exposed three flaws, and all three were fixed with measured justification:

ThresholdBefore → AfterEvidence that drove the change
Duplicate frame (mean abs gray diff, 0–255)0.20 → 0.05Sensor and encoder noise keep consecutive real frames ≥ ~0.08 apart even in a still scene, while true repeats measure ~0.002. The old value raised 90 false duplicates on one static clip; the new one raises 0 and still finds every injected freeze.
Motion jumpany 1.75–6× spike → isolated spikeA hidden drop is one sudden jump. Several elevated differences in a row are genuine motion. Requiring both neighbours to stay below 1.4× the local median cut false hints on real clips from 12 to 2.
Decoder errorsall ffmpeg errors → source onlyIrregular phone timestamps made ffmpeg's output muxer warn while writing thumbnails, which marked a good phone clip DEGRADED. These lines are now kept as pipeline notes.

08 Limitations

  • A byte-perfect transfer cannot prove the original recording had no dropped frames. This is stated in every report.
  • If frames were dropped and the video was then re-encoded with regenerated constant-rate timestamps, the timestamp evidence is gone. Only a low-confidence motion hint remains (V4); confirming it needs a capture-side reference.
  • Duplicate detection cannot tell a frozen capture from a truly still scene, so confidence is lowered for static scenes.
  • The motion-jump hint overlaps with real motion: a hidden one-frame drop scores 1.9× local motion, and handheld motion in real clips reaches ~1.8×. That is why it is never reported as a confirmed anomaly.
  • The chaos proxy emulates loss at TCP level (stalls, resets, slowdowns), not as individual dropped IP packets.
  • Detection accuracy is measured on synthetic ground truth. Real clips show only that the pipeline is sound.
  • No authentication or TLS: this is a challenge prototype, not a hardened service.

09 Future work

  • Adaptive chunk size driven by measured throughput, so a good link pays less per-request overhead.
  • Localise decoder errors to timestamps in the corrupt-bitstream case.
  • A server-restart-mid-upload scenario, and packet-level loss via tc netem.
  • Capture-side frame counters or signed timestamps from the recording app, to close the V4 gap.
  • TLS, authentication and object-storage backing for production use.
